### XBTune additions (XB)

These are robustness changes, not protocol facts:

- The frame decoder resyncs on the next SOH after a bad frame. EcmDroid
  drains its input instead.
- Frames sent by the host (echoes from half-duplex adapters) and frames from
  other addresses are ignored while waiting for a reply.
- Retries: up to 3 attempts for reads; **actuator commands are never
  retried**. After a failed attempt the input is drained for 150 ms so a
  late reply can't answer the next request.
- Link stats: RTT (EWMA 1/8), error rate over the last 50 attempts.

### Test vectors

- `TestPDU`: version reply, GET request/reply, SET request, function
  request (Fan). Ported to `crates/xbtune-proto/src/pdu.rs`.
- `TestEEPROM`: BUEIB page starts. Ported to `crates/xbtune-proto/src/eeprom.rs`.
- Version and runtime request frames (`…56:03:E8`, `…43:03:FD`) are computed
  from the ED rules, not captured. **Confirm against a btsnoop capture.**

### XBTune's reading of the data (XB, not from EcmDroid code)

EcmDroid shows tables and maps only as raw bytes, so their layout is not
defined by its code. XBTune reads them from the database columns and checks
the result for consistency. **Unconfirmed until checked against a
known-good source:**

- **Maps:** `rows` rows of `cols` elements; each row is followed by `skip`
  unused bytes (fuel maps: 13 values + 1 pad). Checked: `rows * (cols *
  width + skip) == size` for every map; BUEIB fuel/spark maps decode with
  monotonic axes and plausible values.
- **Map axes:** `xaxis` runs along a row (columns), `yaxis` down (rows).
  Checked: axis lengths match `cols`/`rows` for every map.
- **Tables (`Table` type):** `rows` interleaved (input, output) pairs; input
  uses `axisscale`/`axistranslate`, output uses `scale`/`translate`.
  EcmDroid applies `scale`/`translate` to both columns. For tables where the
  two differ, which is right is **unconfirmed**; `show` says so.

### Deliberate deviations from EcmDroid

- A 2- or 4-byte `Value` whose `elemsize` is 0 or missing is read as one
  little-endian number. EcmDroid's `Variable.setWidth()` makes it 1, so it
  shows such values as byte lists. Affects all of BUEGC's 2-byte values
  (its db rows have no element sizes; e.g. `LFuel` = AFV, `KTE_Hot`) and
  BUEOD's `KRPM_TCC_Setpoint`.
- Stored codes from the EEPROM (`HDiag<n>`) skip a missing `n` instead of
  stopping there (`ECM.getErrors()` stops): BUEGC has `HDiag1`-`HDiag3`
  but no `HDiag0`.
- `Variable.getHigh()` multiplies `high` by `scale` again when `uhigh` is the
  full raw range. Every `rtoffsets.high` in the data is already in
  engineering units (1,142 equal `uhigh * scale + translate`, the other 102
  are round display limits), so XBTune uses `high` as stored.
- Duplicate `(category, varname)` rows: EcmDroid takes whichever SQLite
  returns first. XBTune keeps the lowest `uniqueid` when duplicates agree on
  type/size/offset, and **drops the variable** when they don't (BUEOD
  `KVS_RPM_Revs`: offset -24 size 1 vs offset 477 size 2).
- Shape problems found on load (e.g. BUE1D/BUEYD `Tab_Idle_Spark`, whose
  rows x cols don't fit its size) leave the variable as raw bytes only.
  `xbtune-cli defs <ID>` lists them.

## Wideband (`crates/xbtune-proto/src/isp2.rs`, `crates/xbtune-core/src/wideband.rs`)

Not from EcmDroid. Source: Innovate Motorsports, "Innovate Serial Protocol
2 (ISP2) specification (preliminary)", 5/3/2004 (public; copy at
<https://github.com/ohhorob/arduino-MTS/tree/master/doc>, file
"Innovate Serial Protocol 2 Specification.pdf", SHA-256
`c0ebc3c8dff7f3a19d64b6ab2bf4ff9b4da88852c1e3f4e41d70d67a3bec475f`). The
spec text only was used; no code from other ISP2 implementations.

| Fact | Spec section |
|---|---|
| 19200 baud, 8N1 | 1 |
| Packets every 81.92 ms; 16-bit big-endian words; both header bytes have the high bit set | 2 |
| Header: bits 15, 13, 9, 7 = 1; bit 14 recording; bit 12 sensor data (0 = command response); length in bits 8 and 6..0, in words after the header | 2, "Header Word" |
| LC-1 sub-packet: 2 words; word 0 = 0 1 0 F2 F1 F0 1 AF7 0 AF6..AF0; word 1 = 0 0 L12..L7 0 L6..L0 | "LC-1 Sub-Packet format" |
| LM-1 sub-packet: 8 words (function, lambda, battery, 5 aux), word 0 bit 15 set, bits 13, 9, 7 clear | "LM-1 Sub-Packet format" |
| Function codes 000 lambda, 001 O2 % x10, 010 free-air calibration, 011 needs calibration, 100 warming %, 101 heater calibration, 110 error code, 111 reserved/flash | 2.1 |
| Lambda = (L + 500) / 1000; AFR = (L + 500) x AF / 10000; AF = stoich x 10 (147 petrol) | 2.1, 2.2 |
| The first wideband device's AF multiplier applies to all | "LC-1 Sub-Packet format" |
| Other devices add data words 0 0 D12..D7 0 D6..D0 | "Other data source sub-packets" |

Innovate sells the LC-2 as an MTS device (its manual, 11-0137C, could not
be downloaded here). That it sends the LC-1 sub-packet above is ASSUMED
until a real LC-2 has been logged. Error code meanings are device-specific
and not in the spec, so XBTune shows the number only. XBTune never sends
commands to the chain.

XBTune choices (not from a source; no real controller tested yet):
- A reading goes on an ECM sample if it is at most 300 ms old.
- Auto-tune with a wideband: correction = EGO / 100 x measured lambda /
  target lambda. ASSUMED: in open loop the EGO value (held at AFV) is
  applied to the fuel. Default sensor delay 0.2 s; default targets by load
  40: 14.7, 60: 14.0, 80: 13.5, 100: 13.2, 125: 13.0 (stoichiometric in the
  light-load closed-loop area, richer with load). These are starting points
  for the owner to adjust, not Buell data.
- Lean warning: average AFR above 14.0 in a cell at load 80 or more.

## Simulator assumptions (ASSUMED, sim only)

These are made up for the simulator and are **not** known ECM behaviour.
Nothing outside tests may rely on them.

- Refused requests are answered with status 0x15. Real error codes are
  unknown.
- Runtime frames for ECMs other than BUEIB are zeros with an ACK.
- The "running engine" (`xbtune-sim/src/engine.rs`) is a made-up 30 s ride
  written through the definition's offsets and scaling. Its values are
  plausible only; they are not reference data for anything.
- Missing page 0 bytes in an image are served as zeros.
- After an active test or TPS reset the busy state reads 1 (the real
  non-zero value is unknown) for `busy_time()`: tachometer 4.2 s and fan
  5.2 s are MEASURED on the owner's BUEIB (done after 4.4 s / 5.4 s with
  500 ms polling, 2026-10-14); other functions 4.5 s ASSUMED.
- Clear codes zeroes the runtime `HDiag<n>_LD` bytes immediately; current
  codes (`CDiag`) stay. (On the owner's BUEIB, 2026-10-14, clearing stored
  code 15 worked and the re-read showed none.) What the real ECM does to `RDiag`/EEPROM `HDiag` is
  unknown.
- Runtime data is answered normally while busy.
- The simulated LC-2 (`xbtune-sim/src/wideband.rs`) warms up for 6 s, then
  sends a made-up lambda for the made-up ride (`engine::lambda_at`), and
  free-air O2 (20.9%) with the engine stopped.
- The made-up ride reports Accel Corr. 0% (it was 100%, which auto-tune's
  filter reads as acceleration enrichment); the owner's logs show 0 when
  steady.
